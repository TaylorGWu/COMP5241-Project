# 需求桌面研究与内部假设工作坊

## 目的与证据边界

本文档是 COMP5241 小组项目需求获取的第一个内部阶段。

它借助公开可获取的产品文档,以及一场由五名成员参与的利益相关者角色工作坊,来识别候选需求和产品机会。它**并不**把这些假设当作真实的用户访谈结论来报告。任何标注为 `Hypothesis` 的结论,都必须在此后通过面向项目组外部人员的原型可用性测试加以检验。

## 研究问题

> AI 辅助的迷你课程平台如何帮助学生以合适的难度学习软件工程相关主题,同时让教师能够高效地创建、改进和监控互动学习活动?

## 1. 桌面研究:现有平台

### 对比概览

| 平台 | 其公开文档中的证据 | 可借鉴的有用思路 | 有意为之的项目机会 / 边界 |
| --- | --- | --- | --- |
| GPTutor | 支持文档对话、练习题、模拟、测验、抽认卡、进度回顾、课程管理和成员管理。其教师工作流可根据材料生成教程草稿、允许直接编辑,并在发布带版本的教程的同时记录学生会话。 | 把 AI 输出视为草稿,由教师在发布前编辑;将学习内容与活动和进度数据结合起来。 | 不要试图照搬一个通用平台。应聚焦软件工程迷你课程,并明确呈现教师审核环节、学习者路径和需求获取活动。 |
| Coursera | 公开介绍了帮助学习者继续课程、并基于其学习历程和目标给出推荐的个性化浏览/首页。 | 学习者应当看到一个清晰的“继续”或“下一步”,而不只是一个庞大的课程目录。 | 采用基于所填目标、背景和近期活动的透明而简单的推荐规则;不要宣称实现了复杂的推荐算法。 |
| Teachnow AI | 公开介绍了自适应课程路径、进度跟踪、学习者自建计划,以及跨多个学科的 AI 辅助学习。 | 基于目标的路径能让宽泛的学科显得易于上手。 | 首个版本不包含语音辅导,也不追求宽泛、无限制的学科覆盖。应支持少量精选的软件工程课程,再加上一个有明确边界的自学路径演示。 |
| EvoClass | 公开展示了结构化的 AI 素养学习内容,涵盖提示词、专用 agent、人机共创和伦理。 | AI 辅助学习应涵盖负责任的使用和实际的人机协作,而不只是工具操作。 | 加入一门 AI 编程 agent 或需求获取的迷你课程,并配有明确的学习成果和反思活动。 |

### 桌面研究得出的设计启示

1. 仅有庞大的课程目录并不能给初学者提供指引。学生仪表盘应当展示一个清晰可见的**推荐下一步操作**。
2. AI 生成的课程内容应是私密、可编辑的**草稿**,而不是被自动发布的学习材料。
3. 活动应当给出讲解和可执行的下一步,而不只是一个分数。
4. 平台需要一个有限而鲜明的聚焦点。首个版本应覆盖软件工程学习,而不是试图做成面向所有学科的通用 LMS。
5. 团队应实现一个有特色的互动活动,而不是许多浅尝辄止的活动类型。

## 2. 内部利益相关者角色工作坊

### 目的

在动手构建之前,由五名项目成员对团队的假设发起挑战。每位成员临时代表一个利益相关者视角。这是一场**内部设计工作坊**,而不是外部用户访谈。

### 角色卡

| 工作坊角色 | 场景 | 假定的痛点 | 候选需求 | 用于质疑该假设的关键问题 |
| --- | --- | --- | --- | --- |
| 非计算机专业初学者 | 因小组作业需要使用 Git,但技术词汇量很少。 | 冗长且千篇一律的课程让人望而生畏;不知道从哪里开始。 | 简短的入门诊断,以及解释清晰的初学者路径。 | 真正的障碍是术语、时间不足、害怕出错,还是别的什么? |
| 计算机专业学生 / 求职者 | 希望为 AI 时代的软件开发工作做准备。 | 懂语法,但在需求、验证、协作和编程 agent 方面缺乏实践。 | 基于场景的练习,并针对推理过程给出反馈,而不只是知识性测验题。 | 学生真的会完成角色扮演活动吗?什么样的反馈才有用? |
| 教师 | 需要把现有课件或笔记变成一节简短的互动课。 | 编写题目、讲解以及材料的多个版本很耗时。 | AI 生成的可编辑草稿、预览,以及受控发布。 | 哪些部分可以安全地交由 AI 起草,哪些部分始终需要人工审核? |
| 助教 | 帮助遇到困难的学生,并希望识别出常见的理解误区。 | 很难知道谁不活跃,或哪个概念导致了错误。 | 按课程/模块/活动查看完成情况、分数和常见错误。 | 哪些指标能真正改变干预决策,而不是产出一堆无人使用的图表? |
| 平台管理员 / 质疑 AI 质量者 | 负责用户访问权限和声誉风险。 | AI 可能产出不准确、不安全或不合适的内容;访问权限也可能配置错误。 | 角色、便于审计的生成记录、验证、人工审核,以及安全的报错信息。 | 当 AI 输出格式错误、缺乏依据或事实存疑时,必须怎么处理? |

### 90 分钟工作坊议程

1. **10 分钟 - 回顾证据边界:** 就以下每一条陈述都是假设、而非已证实的用户事实达成一致。
2. **15 分钟 - 个人角色准备:** 每位成员阅读一张角色卡,并写下最重要的三项需求、担忧和成功标准。
3. **20 分钟 - 现状流程梳理:** 每个角色说明在没有该平台的情况下,任务是如何完成的。
4. **20 分钟 - 原型评析:** 每个角色走查计划中的学生或教师流程,并指出缺失的信息、失败情形和令人困惑的决策点。
5. **15 分钟 - 优先级排序:** 用 Must / Should / Could / Won't 为候选功能打分。
6. **10 分钟 - 决策记录:** 记录改了什么、为什么改、负责人以及证据来源。

### 工作坊记录模板

| 假设 ID | 利益相关者角色 | 假设 | 证据类型 | 决策 | 后续验证 |
| --- | --- | --- | --- | --- | --- |
| H-01 | 非计算机专业初学者 | 基于目标和背景的入门引导流程能改善首节课的选择。 | 桌面研究 + 内部工作坊 | 纳入原型 | 之后与外部学生一起测试任务完成情况 |

## 3. 候选假设与需求

### 待检验的假设

| ID | 假设 | 候选功能 | 验证任务 |
| --- | --- | --- | --- |
| H-01 | 相比庞大的课程目录,初学者更需要一个清晰的起点。 | 入门引导,加上推荐的下一门迷你课程。 | 请一位参与者在无人协助的情况下找到合适的第一门课程。 |
| H-02 | 相比只有一个分数,学生从讲解和下一步建议中获益更多。 | 包含正确答案解析和推荐后续课程的反馈卡。 | 比较参与者在答错后能否说出接下来该做什么。 |
| H-03 | 只有在学生看到之前能够检查和编辑,教师才会使用 AI 生成的内容。 | AI draft -> edit -> preview -> publish 工作流。 | 请一位教师/助教创建一门课程,并指出信任方面的顾虑。 |
| H-04 | 教师需要可据以行动的学习参与信息,而不是满是虚荣指标的仪表盘。 | 完成率、最常答错的题目,以及不活跃学生名单。 | 询问教师哪张图表会改变他们的下一步行动。 |
| H-05 | 当学生向模拟的利益相关者提问时,需求获取练习会变得更有吸引力。 | 受控的 AI 角色扮演,并配有一份涵盖问题、现有流程和异常情况的评分表。 | 观察学生能否解释反馈,并在第二次尝试中有所改进。 |
| H-06 | AI 课程生成必须被约束为可预期的结构化输出。 | 由服务端校验的 JSON 课程草稿,并带有重试/错误状态。 | 测试格式错误和不完整的 AI 响应。 |

### 候选功能需求

| ID | 需求 | 优先级 | 验收信号 |
| --- | --- | --- | --- |
| FR-01 | 学生可以创建账户,并且只能访问学生功能。 | Must | 学生无法打开教师/管理员的路由或 API。 |
| FR-02 | 学生可以填写背景和目标,然后获得推荐的入门课程。 | Should | 仪表盘展示下一门课程,并说明推荐理由。 |
| FR-03 | 学生可以完成一节课和 MCQ 活动,然后获得解析和进度更新。 | Must | 刷新后,作答记录、分数和完成状态仍然保留。 |
| FR-04 | 教师可以创建、编辑、预览并发布一门迷你课程。 | Must | 已发布的内容对已选课学生可见;草稿不可见。 |
| FR-05 | 教师可以根据主题、受众、学习成果和时长,让 AI 生成结构化的、可编辑的课程草稿。 | Must | AI 输出以可编辑草稿的形式展示;无效输出会产生可恢复的错误。 |
| FR-06 | 教师可以查看课程完成情况、平均分和常见错误答案。 | Must | 仪表盘统计与存储的选课记录和作答记录一致。 |
| FR-07 | 教师可以通过经过校验的小型 CSV 导入或邀请码添加学生。 | Should | 有效用户被成功选课;无效行会收到明确的错误提示。 |
| FR-08 | 学生可以完成一次基于场景的需求获取活动,并获得基于评分表的反馈。 | Could | 反馈能指出对问题、现有流程和异常情况的覆盖程度。 |

### 候选非功能需求

| ID | 需求 | 优先级 |
| --- | --- | --- |
| NFR-01 | 学生和教师的主要流程在桌面端和移动端尺寸的屏幕上均可正常使用。 | Must |
| NFR-02 | 基于角色的授权由后端强制执行,而不只是在前端隐藏。 | Must |
| NFR-03 | LLM API 密钥仅存放在后端环境变量中。 | Must |
| NFR-04 | 在教师发布之前,AI 生成的内容会被明确标注为草稿。 | Must |
| NFR-05 | 面向用户的 AI 错误会说明发生了什么,并提供重试/编辑选项,同时不泄露任何密钥。 | Must |

## 4. 推荐的 MVP 决策

### 优先构建

```text
Instructor creates/publishes a Git Basics mini-course
-> Student joins it
-> Student completes a lesson and MCQ
-> System stores progress and score
-> Instructor sees completion and common-mistake data
```

之后再加入 AI 课程草稿工作流。只有在端到端切片稳定之后,才加入基于场景的角色扮演。

### 明确不在 MVP 范围内

- 实时视频课或语音辅导。
- 支付、证书、社交动态、论坛和聊天内容审核。
- 完整的 LMS 兼容性或全学科内容覆盖。
- 不受限制的通用聊天机器人。
- 复杂的机器学习推荐系统。

## 5. 下一步验证

内部工作坊应当产出初始原型及其假设。在最终展示之前,条件允许时应与至少 2-3 名组外人员开展简短的、基于任务的原型测试。

建议任务:

1. “你是 Git 新手。请找到一门合适的入门课程,并完成其中的第一道题。”
2. “你是一名教师。请生成一门短课程,检查 AI 草稿,修改其中一处内容,然后发布它。”

只记录必要的内容:任务是否完成、犹豫点、观察到的问题、参与者原话(经其同意)、设计改动,以及改动前后的原型证据。
