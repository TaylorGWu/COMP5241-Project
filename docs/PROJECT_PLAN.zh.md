# COMP5241 项目计划

## 0. 当前项目方向

**当前设想:** 一个由 AI 辅助、用于学习软件工程的迷你课程平台。

该平台应能让教师借助 AI 创建并打磨互动式迷你课程,同时让学生获得与其背景和目标相匹配的学习内容、活动、反馈以及后续学习建议。

这只是一个当前方向,并非最终的产品名称或范围决定。小组应在需求获取阶段对其加以验证,然后再确定是否投入实现。

### 主要用户角色

| 角色 | 主要目标 | 核心能力 |
| --- | --- | --- |
| 学生 | 以合适的难度学习软件工程相关主题 | 入门引导、课程学习、活动、反馈、进度、推荐 |
| 教师 | 高效创建和管理互动式迷你课程 | AI 课程草稿生成、编辑、发布、学生管理、分析 |
| 管理员 | 维持平台的基本运转 | 用户与课程总览;基本的内容审核/管理 |

### 建议的 MVP 用户流程

```text
Instructor creates and publishes a Git Basics mini-course
  -> Student joins the course and completes a lesson plus MCQ activity
  -> System stores the attempt, score, and progress
  -> Instructor sees completion rate and common incorrect answers
```

在添加更高级的 AI 功能之前,先把这个端到端流程搭建起来。

## 2. 需求获取与分析

### 目标

- 在决定开发哪些功能之前,先找出真实的学习与教学问题。
- 从学生处收集证据;如有可能,也收集教师、助教或导师的证据。

### 利益相关者

| 利益相关者 | 需要了解的内容 |
| --- | --- |
| 非计算机专业学生 | 技术学习在哪些环节变得令人困惑或容易让人放弃 |
| 计算机专业学生 / 求职者 | 哪些软件工程或 AI 时代的职业能力需要更多练习 |
| 教师 / 助教 | 目前如何制作互动材料、如何监测学习进度 |

### 访谈提纲

- 你目前如何学习一个不熟悉的软件工程主题?
- 这一过程中哪一部分困难、缓慢或容易让人放弃?
- 哪些信息能帮助你判断接下来该学什么?
- 你目前如何制作或寻找练习与互动学习内容?
- 如果由 AI 来协助你,你会把哪些工作交给它,又有哪些工作仍希望自己审核?
- 当某位学生的知识背景与班上其他人差别很大时,会出现什么情况?

### 任务

- [ ] 访谈 3-5 名学生,并在可能的情况下访谈一位教师/助教。
- [ ] 记录符合知情同意要求的笔记、匿名引语和观察到的痛点。
- [ ] 根据调研结果创建 2-3 个用户画像。
- [ ] 梳理每个用户画像的当前工作流程、痛点、需求和约束条件。
- [ ] 将调研结果转化为候选的功能需求和非功能需求。

### 产出

- 访谈提纲与访谈笔记。
- 利益相关者地图与用户画像。
- 痛点清单。
- 附来源证据的需求清单。
- 初步案头调研与内部假设研讨:[REQUIREMENTS_DESK_RESEARCH.md](REQUIREMENTS_DESK_RESEARCH.md)。
- 含公开视觉证据的独立竞品分析:[competitor_analysis/README.md](competitor_analysis/README.md)。

### 完成标准

- 团队能够说明:谁遇到了问题、在什么情境下遇到问题,以及现有做法为何不够。

## 3. 定义问题、MVP 范围与优先级

### 问题陈述草稿

> 软件工程背景各不相同的学生需要合适且具互动性的学习路径,而教师需要更快捷的方式来创建、打磨并监测此类学习活动。

### 用户故事示例

- 作为学生,我希望选择自己的经验水平和学习目标,以便获得合适的入门课程。
- 作为学生,我希望在完成活动后立即看到解析,以便理解某个答案为什么正确或不正确。
- 作为教师,我希望由 AI 生成可编辑的课程草稿,以便更快地准备互动材料,同时仍能掌控质量。
- 作为教师,我希望查看完成情况和表现数据,以便找出需要帮助的学习者和主题。

### MoSCoW 优先级建议

| 优先级 | 范围 |
| --- | --- |
| **Must** | 基于角色的登录、课程目录、课程播放器、MCQ、进度跟踪、教师创建/编辑/发布课程、基本分析、一项 AI 课程草稿功能 |
| **Should** | 学生入门引导与推荐、CSV 学生导入 |
| **Could** | 徽章、学习者自建的私人学习路径 |
| **Won't for this release** | 支付、直播课、社交动态/论坛、不受限制的 AI 导师、复杂的推荐算法 |

### 任务

- [ ] 回顾访谈发现,并修订问题陈述。
- [ ] 就主要用户和单一 MVP 流程达成一致。
- [ ] 最终确定用户故事与验收标准。
- [ ] 以小组形式确认 Must/Should/Could/Won't 范围。
- [ ] 把每一项 Must 功能转为一个 GitHub Issue。

### 完成标准

- 小组就最终原型要做什么、不做什么达成一致。

## 6. 系统设计

### 建议的架构

```text
Next.js frontend
    -> REST API
FastAPI backend
    -> PostgreSQL database
    -> JWT authentication and role-based access control
    -> AI generation / feedback service
    -> File storage service
```

### 建议的技术栈

| 层次 | 技术 |
| --- | --- |
| 前端 | Next.js、TypeScript、Tailwind CSS |
| 后端 | Python、FastAPI、Pydantic |
| 数据库 | PostgreSQL |
| ORM / 迁移 | SQLAlchemy + Alembic,或 SQLModel |
| 认证 | JWT + 密码哈希,或与 FastAPI 集成方式清晰的可托管认证服务 |
| AI 集成 | 仅由后端调用 LLM API;返回经过校验的结构化 JSON |
| 图表 | Recharts 或同类前端图表库 |
| 部署 | 前端用 Vercel;FastAPI 用 Render/Railway 或同类服务;托管 PostgreSQL |

### 核心数据模型

```text
profiles: user identity, role, background, learning goals
courses: course metadata, author, status
modules / lessons: course structure and learning content
activities / questions / options: learning interactions
enrollments: student-course membership and completion state
activity_attempts: submitted answers, score, feedback, timestamps
course_generations: AI request, generated draft, review/publication state
```

### 设计任务

- [ ] 绘制架构图。
- [ ] 绘制 ERD 并制定数据库迁移计划。
- [ ] 定义 API 契约和错误响应。
- [ ] 制作角色权限矩阵。
- [ ] 定义 AI 输入、输出 JSON schema、校验、重试和人工审核步骤。
- [ ] 记录环境变量与密钥管理规则。

### 完成标准

- 每个页面和每项用户操作都有明确的 API、业务负责人和数据库影响。

## 7. 开发与集成

### 开发准则

在扩大范围之前,先构建一个可运行的垂直切片:

```text
Instructor creates and publishes a course
-> student joins it
-> student completes a lesson and MCQ
-> backend records progress
-> instructor sees analytics
```

### 五人模块分工

| 成员 | 主要负责 | 协助贡献 |
| --- | --- | --- |
| 成员 A | 学生端:入门引导、仪表盘、课程目录、路径推荐 UI | 需求调研与 UI/UX 验证 |
| 成员 B | 课程播放器:课程、MCQ、情景活动、反馈、进度 UI | 学生流程测试 |
| 成员 C | 教师端:AI 课程构建器 UI、编辑器、发布、CSV 导入 | 教师可用性测试 |
| 成员 D | FastAPI 与数据:认证、RBAC、课程/选课/作答 API、PostgreSQL | ERD、API 文档、分析查询 |
| 成员 E | AI 与质量:生成端点、JSON 校验 | 部署、集成测试、发布就绪 |

### 共同职责

- [ ] 每位成员实现一项可单独演示的功能,并通过 PR 提交。
- [ ] 每位成员至少审核另一位成员的一份 PR。
- [ ] 每位成员为自己负责的功能编写测试文档。
- [ ] 每位成员都参与用户测试、最终报告和汇报。
- [ ] 频繁合并;不要把集成留到最后一周。

### 横切的工程要求

这些不是优先级候选 —— 不做系统就跑不起来,所以记在这里,不拿去投票。

- [ ] 数据库持久化与迁移。
- [ ] 登录与角色授权,由后端强制(越权访问返回 403)。
- [ ] 长耗时生成不阻塞请求(后台作业队列)。
- [ ] 响应式:320px 宽可用,不出横向滚动条。
- [ ] 键盘操作与无障碍:所有操作可键盘完成,每张图有替代文本。
- [x] 单点失败不拖垮整包。
- [x] 密钥只存后端环境变量。
- [x] 模型用量(token、估算成本)可观测。
- [x] 三语言界面(英文、繁體中文、简体中文)。

### 完成标准

- 完整的 Must 功能用户流程可在共享的部署环境中运行。

## 8. 测试与部署

### 测试清单

- [ ] 认证与角色保护:学生无法访问教师/管理员功能。
- [ ] 授权:教师无法编辑其他教师的课程。
- [ ] 课程发布、选课、活动作答、得分和进度都能正确持久化。
- [ ] AI 输出无效、超时和 API 失败时,能向用户显示有用的错误提示。
- [ ] CSV 导入在保存前会校验格式错误的数据。
- [ ] 主要流程在桌面端和移动端尺寸下均可正常使用。
- [ ] 用户能够完成既定的验收测试任务。

### 部署任务

- [ ] 为开发环境和生产环境分别创建环境变量。
- [ ] 部署前端、后端和数据库。
- [ ] 验证生产环境 API、认证重定向和 CORS 配置。
- [ ] 在 README 中添加公开 URL 和搭建步骤。
- [ ] 在公开部署环境上重新测试完整的垂直切片。

### 需保留的证据

- 测试用例/结果、缺陷报告、修复记录、部署 URL、截图或录屏,以及 CI 输出(如使用)。
